# 更夫 × 夜莺（Nightingale / FlashCat）能力对标

> 对标对象：夜莺监控 v8/v9（快猫星云 FlashCat 同源开源版，n9e.io）。
> 定位先行：夜莺是**监控告警引擎**（采集判定层），更夫是**告警之后的平台**（聚合响应层）——
> 两者是上下游关系而非竞品，本文对标的是「用户从夜莺迁移/组合使用时，更夫补不补得上」。

## 一、能力矩阵

| 能力 | 夜莺 v8/v9 | 更夫现状 | 差距结论 |
|---|---|---|---|
| 多数据源告警规则判定 | ✅ 强项（Prometheus/VM/ES/CH 等 10+） | ❌ 不做（定位边界） | 不补，监控层留给夜莺 |
| 告警接入汇聚 | ✅ 内置 | ✅ 477 个 provider + webhook | 等价 |
| 去重降噪关联 | 基础聚合 | ✅ 指纹去重 + CEL 关联 + AI 关联 | 更夫强 |
| 通知规则（媒介模板化） | ✅ 规则上直配钉钉/短信/电话/HTTP/脚本 | ⚠️ 用工作流表达，能力等价但配置门槛高 | 可吸收 |
| 订阅规则（个人订阅） | ✅ 按等级/规则订阅事件 | ❌ 无 | **建议 P1 吸收** |
| 屏蔽/静默规则 | ✅ 屏蔽规则 | ✅ 维护窗口（maintenance windows） | 等价 |
| 事件中心 | ✅ 事件列表/认领 | ✅ 更完整（关联、时间线、AI 报告） | 更夫强 |
| 自愈（告警触发脚本） | ✅ ident + 权限校验 | ⚠️ 工作流可做（bash/http/python provider），缺模板化 | 可补文档/模板 |
| 值班排班 | ❌ 本体无（FlashDuty 才有） | ✅ P1-P3 已落地（排班/认领/升级/MTTA） | **更夫强** |
| 仪表盘可视化 | ✅ 内置大盘 | ❌ 无 | 不补（可视化归 Grafana） |
| AI 分析 | ❌ 无原生 LLM | ✅ 国产模型直连、中文报告 | **更夫强** |
| 中文化 | ✅ | ✅ | 等价 |

## 二、建议吸收的三件事（按优先级）

### P1：订阅规则（个人告警订阅）

夜莺用户最顺手的「我关心某类告警，私聊通知我」能力，更夫目前只能靠管理员建工作流实现。

- 形态：告警页/事件页加「订阅」入口 → 按预设/CEL/等级过滤 → 通知走钉钉/企微/飞书私聊或邮件；
- 数据模型复用：订阅表（user_id + CEL + 媒介 + 静默时段），引擎侧用现有工作流触发器翻译执行；
- 验收：普通用户（非管理员）3 分钟内自助完成一条订阅并收到第一条私聊通知。

### P2：通知向导（把工作流翻译成表单）

更夫的通知能力不输夜莺，但要求用户理解工作流 YAML——门槛高于夜莺的通知规则表单。

- 形态：不做新引擎，做「通知模板向导」：选触发条件（预设/CEL）→ 选媒介（钉钉/企微/飞书）→ 填 webhook → 保存为工作流；
- 本质是 gengfu-* 内置模板的表单化包装，复用度极高。

### P3：自愈模板库

工作流引擎能力等价于夜莺自愈，缺的是开箱即用的模板与文档：

- 补 2-3 条 gengfu-heal-* 模板（如「高危告警自动执行处置脚本 + 结果回写事件」），文档给夜莺自愈的迁移对照。

## 三、明确不跟的

- **多数据源告警判定**：定位边界，监控层继续交给夜莺/Prometheus/Zabbix；
- **内置大盘**：可视化归 Grafana，更夫的差异化在告警后链路与 AI。

## 四、一句话卖点（对外口径）

夜莺管「告警的产生」，更夫管「告警的一生」：聚合降噪、值班通知、事件管理、AI 分析、自动处置——并补上夜莺本体没有的值班排班与 AI 能力。
